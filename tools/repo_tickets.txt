Title: Add -NoConfig switch (pass --no-config to dcc32)
Issue: #11
Status: closed
Labels: enhancement
Body:
## Problem

The script never passes `--no-config`, so `dcc32` auto-loads
`<RootDir>\bin\dcc32.cfg`. In portable/trimmed toolchains that cfg frequently
carries stale absolute library paths (or `$(BDS)`-relative paths captured from
another machine), which silently injects wrong or duplicate `-U`/`-I` entries.
The legacy batch system (`rad-buildfiles-shared\DelphiBuild.bat`) passes
`--no-config` and supplies every path explicitly, which is why it is
reproducible across machines.

## Proposed

A `-NoConfig` switch that appends `--no-config` to the dcc32 command line.
Opt-in; default behavior (cfg auto-loaded) is unchanged.

## Acceptance criteria

- [ ] `-NoConfig` appends `--no-config` to the dcc32 invocation
- [ ] With `-NoConfig`, dcc32 does not read `dcc32.cfg`
- [ ] Units/includes resolve only from the paths the script and its params provide
- [ ] Omitting the switch preserves current default (cfg auto-loaded)

Title: Add resource/package output switches (-R, -LE, -LN, -NB, -LU)
Issue: #12
Status: closed
Labels: enhancement
Body:
## Problem

The script exposes `-U`/`-I`/`-NS`/`-D`/`-E` and a DCU output dir, but not:
`-R` (resource dirs), `-LE` (.bpl output), `-LN` (.dcp output), `-NB` (.bpi
output), `-LU` (used runtime packages). Projects that reference resource
directories or that build/consume packages cannot be built today.

## Proposed params

- `-ResourcePath <string[]>`  -> `-R<;-joined>`
- `-BplOutputDir  <string>`   -> `-LE<dir>`
- `-DcpOutputDir  <string>`   -> `-LN<dir>`
- `-BpiOutputDir  <string>`   -> `-NB<dir>`
- `-LinkPackage   <string[]>` -> `-LU<;-joined>` (used runtime packages)

## Important flip side of -LU

Linking runtime packages makes the output depend on `rtlNNN.bpl` /
`vclNNN.bpl` at load time. The current default (no `-LU`, i.e. statically
linked) MUST remain the default so standalone exes keep working. Observed
concretely: an exe built with `-LUrtl` failed to load with `0xC0000135`
because `rtl140.bpl` was not on the target. `-LinkPackage` must be strictly
opt-in.

## Acceptance criteria

- [ ] Each param maps to the correct dcc32 switch
- [ ] Omitting a param omits the corresponding switch
- [ ] Multiple paths/packages are `;`-joined into a single switch
- [ ] Static (default, no `-LU`) standalone exes still build and load
- [ ] Package-using exes build with `-LinkPackage`

Title: Add -SkipRsvars mode (skip rsvars, honor caller-preset env)
Issue: #14
Status: closed
Labels: enhancement
Body:
## Problem

The script hard-requires `<RootDir>\bin\rsvars.bat` (exit 3 if missing) and
sources it. Two failure modes:

- (a) The oldest toolchains (Delphi 2 / 7 / 2005) have no `rsvars.bat` at all
  -- it predates them -- so they cannot be built even though `bin\dcc32.exe`
  is present.
- (b) A caller may want to set `BDS` / `PATH` / library env itself (exactly
  what `_SetDelphiBuildPaths.bat` does) and NOT have rsvars mutate it.

## Proposed

A `-SkipRsvars` switch that bypasses the rsvars requirement and sourcing, and
runs `dcc32.exe` directly using the current process environment (pre-set by
the caller) plus the explicit `-U`/`-I` paths. Combined with `-NoConfig` and
the resource/package/extra-args switches this reproduces the fully-explicit,
self-contained invocation the batch system relies on.

## Acceptance criteria

- [ ] With `-SkipRsvars`, a `RootDir` that has `bin\dcc32.exe` but no
      `bin\rsvars.bat` builds successfully
- [ ] rsvars is never called when `-SkipRsvars` is set
- [ ] The caller's pre-set environment is honored (not overwritten)
- [ ] Default behavior (rsvars required and sourced) is unchanged when the
      switch is omitted

Title: Run dcc32 from the project's directory so relative in / {$I} / {$R} paths resolve
Issue: #15
Status: closed
Labels: enhancement
Body:
## Problem

`delphi-dccbuild.ps1` invokes `dcc32.exe` in the caller's current working
directory; it does not `cd` into the project (.dpr) folder the way the legacy
batch (`rad-buildfiles-shared\DelphiBuild.bat`) does. Any path the project
resolves against the compiler's working directory then breaks:

- a `uses` reference like `SomeUnit in '..\..\shared\SomeUnit.pas'`
- `{$I ..\common\defs.inc}` include directives
- `{$R ..\res\app.res}` resource directives

Observed concretely: building `radLicenseXPHarness.dpr` (which has
`radLicense in '..\..\verifier\radLicense.pas'`) via `-RootDir` against a
trimmed Delphi 2010 toolchain failed with `F1026 File not found:
'radLicense.dcu'` until the caller manually set the process working directory
to the project folder. The batch avoids this by `cd`-ing into the .dpr
directory before invoking dcc32.

## Proposed

Before invoking dcc32, set the working directory to the folder of the resolved
`-ProjectFile`, and restore the original CWD afterward (even on failure). This
matches the batch and makes relative `in` / `{$I}` / `{$R}` references resolve
as the project author intended.

Add a `-WorkingDirectory <path>` override whose default is the resolved project
file's folder. Callers who need a different CWD (including "don't change dir --
use my current CWD") pass it explicitly. This single knob subsumes a
`-NoChangeDir` switch and is more flexible.

## Implementation notes (confirmed)

1. `Set-Location` / `Push-Location` ALONE will NOT change dcc32's working
   directory on Windows PowerShell 5.1. A native child process inherits
   `[System.Environment]::CurrentDirectory` (the .NET process CWD), which in
   WinPS 5.1 does not track PowerShell's `$PWD` / `Set-Location`. This repo
   targets 5.1 (`tests\pwsh\WindowsPS51Compat.Tests.ps1`), so a naive
   push/pop would pass the mocked test suite but silently fail against a real
   compiler. The implementation MUST set `[System.Environment]::CurrentDirectory`
   (or use `Start-Process -WorkingDirectory`) and restore it in a `finally`.
   Place this inside `Invoke-DccExe`, wrapping the actual `& $CompilerPath`
   call, so the restore is guaranteed on throw.

2. Relative output/search paths change meaning once CWD moves. `ProjectFile`
   is already resolved to absolute before invocation, so it is safe. But
   relative `-ExeOutputDir` / `-DcuOutputDir` / `-UnitSearchPath` /
   `-IncludePath` / `-ResourcePath` / `-BplOutputDir` / `-DcpOutputDir` /
   `-BpiOutputDir` would otherwise anchor to the project dir instead of the
   caller's CWD. Resolve these to absolute against the caller's ORIGINAL CWD
   before the cd so existing callers see no behavior change, and document it.

## Acceptance criteria

- [ ] dcc32 runs with its working directory set to the resolved project file's folder by default
- [ ] `-WorkingDirectory <path>` overrides the default; passing the caller's CWD reproduces the old (no-change) behavior
- [ ] A project with a relative `in '..\..\path\Unit.pas'` reference builds without the caller pre-setting CWD
- [ ] The native compiler's working directory is actually changed on Windows PowerShell 5.1 (not just `$PWD`)
- [ ] The caller's original working directory (`$PWD` and `[Environment]::CurrentDirectory`) is restored after the build, even on failure
- [ ] Relative `-ExeOutputDir` / `-DcuOutputDir` and other relative path params anchor to the caller's original CWD, not the new project CWD, and this is documented
- [ ] Builds that already pass absolute paths are unaffected
- [ ] The result object records the working directory used

Title: Add -OutputFile / -Format for structured result output (parity with delphi-msbuild)
Issue: #16
Status: closed
Labels: enhancement
Body:
## Problem

`delphi-msbuild.ps1` supports `-OutputFile <path>` (writes the result object as
JSON to a file) and `-Format object|json`. `delphi-dccbuild.ps1` has neither --
it only emits the result object to the pipeline.

This breaks the `delphi-powershell-ci` module's DCCBuild engine. Its
`Invoke-BuildPipeline` marshals every build's result by passing
`-OutputFile <temp>` to the bundled tool and reading the JSON back
(unconditional -- same code path for both engines). Because dccbuild has no
`-OutputFile`, `Invoke-DelphiBuild -BuildEngine DCCBuild` fails immediately with:

  delphi-dccbuild.ps1: A parameter cannot be found that matches parameter name 'OutputFile'.

Observed building `radLicenseXPHarness.dpr` against a portable Delphi 10.4
Sydney toolchain via `Invoke-DelphiBuild ... -BuildEngine DCCBuild
-ToolchainRootDir ...`. The same project builds fine via the standalone
`delphi-dccbuild.ps1` (which returns its object to the pipeline), so this is
purely the missing file/JSON output contract.

## Proposed

Add, matching delphi-msbuild's surface and semantics:

- `-OutputFile <string>`  -- write the result object as JSON to this path
- `-Format object|json`   -- default `object` (current behavior); `json` emits JSON

Keep the current pipeline-object output as the default so existing callers are
unaffected. After this lands, re-sync the bundled copy in delphi-powershell-ci.

## Acceptance criteria

- [ ] `-OutputFile` writes the full result object as JSON to the given path
- [ ] `-Format json` emits JSON to the pipeline; `-Format object` (default) is unchanged
- [ ] The JSON fields match delphi-msbuild's so the CI module can read either uniformly
- [ ] Omitting both preserves the current default (object to the pipeline)
- [ ] `delphi-powershell-ci` `Invoke-DelphiBuild -BuildEngine DCCBuild` marshals the result end-to-end
